# 図形の設計判断

図形（オブジェクト）を新設・拡張するときの判断基準。
[設計思想](./01-design-philosophy.ja.md) がコードの書き方の原則を扱うのに対し、
本書は「doc スキーマに何を載せ、何をエンジンに任せるか」という、
コードを書く前の設計判断を扱う。

## ジオメトリは役割で「ユーザー指定」と「エンジン導出」を切り分ける

図形にジオメトリのパラメータ（区画の高さなど）を追加するとき、doc フィールドとして
ユーザーに開放するか、エンジンが導出するかは、その領域の**役割**で決める。

- **外形（bbox）はユーザーが決める**。コンテンツが収まらなくても外形は変えず、
  あふれ・クリップを許容する（矛盾は診断で AI / ユーザーに直させる。エンジンは自動補正しない）
- **テキストを収めるためだけの内部区画**（例: record の name 帯）は**導出**する。
  ユーザーの欲求は「特定の高さ」ではなく「タイトルが読める状態」であり、
  フォントサイズ等からの導出で満たせる
- **操作面・造形を兼ねる区画**（例: container の header。pass-through な本体に代わる
  掴みハンドルであり、専用色を持つ視覚アクセントでもある）は **doc フィールドとして
  手動調整可能**にする。図形全体との釣り合いや掴みやすさは、コンテンツの収まりとは
  独立した正当な調整対象になる

見分け方は「コンテンツが収まれば満足か」。Yes なら導出、
「図形全体との比率・操作性を調整したい」が正当に成り立つなら手動。
手動にする場合も未指定時のデフォルトは導出でよい（導出デフォルト + 手動 override）。

### なぜ

doc フィールドは 1 つ増えるごとに、AI 生成時に整合を取るべき値・矛盾を検出する診断・
編集ジェスチャーとそのテストが連動して増える。導出で満たせる欲求に自由度を与えても
このコストだけが残る。逆に、造形上の正当な欲求を導出で固定すると、図形サイズの
振れ幅（小さな frame から画面を覆う zone まで）に追従できない。

具体例:

- record の name 帯: doc フィールドを持たず導出（`calcRecordSlotRegions`）
- container の header: `headerHeight` doc フィールド + divider ドラッグ
  （`handleContainerHeaderHeight`）。未指定時はデフォルト値で描画
